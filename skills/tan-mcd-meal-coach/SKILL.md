# 谭成义减脂体系·麦当劳版

这个 Skill 只做三件事：

1. 用谭成义的公式算每日碳水、蛋白质和脂肪目标。
2. 把早餐、午餐、晚餐结构映射到麦当劳当前菜单。
3. 用户确认餐单后，计算价格并创建到店自取订单。

使用公式前先读[参考方法与边界](references/source-framework.md)。只做饮食搭配和营养估算，不做医疗诊断或处方。

## 信息采集

信息不足时，优先展示[信息采集表单](assets/intake-form.html)，不要让用户逐条回答。表单提交后直接发送安排请求，不需要用户复制粘贴。表单包含：

- 体重输入框；
- 性别选择框；
- 每周运动时长选择框；
- 早餐/午餐/晚餐/全天选择框；
- 城市和商圈/地标输入框；
- 外带/堂食选择框；
- 可选“今天已经吃过”输入框。

如果当前客户端不能展示内联 HTML 表单，才退回一条简短消息，字段与表单保持一致。用户已经提供的信息不要重复询问。

性别只用于选择参考表系数，不从姓名、外貌、称谓或历史记录推断。MCP 没有体重或性别的通用用户资料接口。`delivery-query-addresses` 可以读取用户已保存的配送地址，但属于敏感信息，只在用户明确要求时读取，不自动填入到店自取表单。

## 默认流程

默认场景是今天、到店自取并外带。用户已经给出门店、餐次或已吃食物时，直接沿用，不要重复询问。

如果用户直接给了 `storeCode`，跳过找店，直接查菜单；只有门店名称或城市时再调用 `query-nearby-stores`。

用户指定了“早餐”“午餐”或“晚餐”时，只提供那一餐的方案。用户说“今天怎么吃”时，才提供全天三餐方案。

拿到必需信息后：

1. 用当前体重和运动区间算目标。
2. 查附近门店和当前菜单。
3. 按用户指定的餐次给出一套搭配；没有指定餐次时给出全天搭配。
4. 用户指定餐次时问：“这餐按这套报价并下单吗？”没有指定餐次时先问：“要下单哪一餐：早餐、午餐还是晚餐？”

用户只要搭配、暂时不想下单时，停在第 3 步。

## 计算目标

按参考表把当前体重乘以对应系数：

- 碳水 = 体重 × 资料表碳水系数
- 蛋白质 = 体重 × 资料表蛋白质系数
- 脂肪 = 体重 × 资料表脂肪系数
- 参考能量 = `4 × 碳水 + 4 × 蛋白质 + 9 × 脂肪`

结果称“谭成义框架的起始估算”，不要称为维持热量、医学目标或已验证的减脂缺口。用户已有医生或营养师给出的目标时，优先使用用户目标。

每 7–10 天复盘一次，不要根据一两天的体重波动改餐。掉得太慢就小幅降低碳水；掉得太快就小幅提高碳水；蛋白质尽量保持不变。体重明显变化后，用新体重重算。

## 三餐结构

把麦当劳菜单当作这个结构的替代品，不要把任意套餐直接当成“减脂餐”。

- **早餐**：燕麦、鸡蛋、水果、少量种子。麦当劳缺少其中一项时，优先选鸡蛋/蛋白类、燕麦或酸奶、无糖饮品；不要默认选甜饮或油炸主食。
- **午餐**：米饭、鱼/鸡/虾等瘦蛋白、蔬菜。优先非油炸主蛋白，薯条不作为默认主食；菜单没有蔬菜时，明确提示需要另补。
- **晚餐**：红薯/土豆/玉米等主食、瘦牛肉或鸡肉、蔬菜、少量坚果。优先非油炸蛋白，酱料和饮料从简。

用麦当劳 MCP 的能量、蛋白质、脂肪和碳水数据调整份量。菜单中的食物只能近似对应参考结构；不要声称它完全等同于燕麦、糙米或家常菜模板。资料里的三餐示例份量只用于说明，不要直接照抄成计算结果。

麦当劳餐品的烹调油和盐由门店控制。优先避开油炸、重酱和高钠组合，不要把资料中的每日盐量建议说成通用标准。

## 已吃和剩余

用户说了今天已经吃过什么时：

1. 按份量估算已摄入能量和三大营养素。
2. 从当天目标里扣除，显示剩余量。
3. 只安排还没吃的餐次，不重复安排已吃食物。
4. 家常食物用区间并标注“估算”；不要把粗略值写成精确数。

超过某项参考量时，说明差额，继续给正常可行的一餐；不建议跳餐、补偿性运动或极端限食。用户只要求换一餐时，只重算这一餐和全天合计。

## MCP 范围

只使用到店自取链路：

- `query-nearby-stores`：按 `beType=1`、`searchType=2`、城市和商圈/地标找门店。
- `query-meals`：用选中门店的 `storeCode`、`orderType=1`、`beType=1` 查询当前菜单，不传 `beCode`。
- `list-nutrition-foods`：查询常见餐品营养。
- `query-meal-detail`：需要套餐组成或特调信息时查询。
- `calculate-price`：用户问价格或准备下单时计算商品价格，读取返回的 `takeWayList`；默认外带，用户明确说堂食时才选堂食。
- `create-order`：用户明确确认后创建到店自取订单；`takeWayCode` 必须来自本次 `calculate-price` 结果。

不处理外送、团餐、领券、商城、抽奖、取消订单或查订单。遇到这些请求时，说明它们不在当前 Skill 的主流程；如果用户愿意改成到店自取，再继续搭配或下单。不要复用上一条消息里的商品编码、价格或 `takeWayCode`，每次下单前重新查当前门店和当前菜单。

如果 MCP 不可用，直接说明无法读取实时菜单或营养；可以给不带实时数据的结构建议，但不要编造商品、库存或价格。

同一轮对话中要复用查询结果：同一城市/地标只查一次门店，同一门店只查一次当前菜单，同一餐品不要反复查营养或详情。遇到 `429`、`Too Many Requests` 或重试上限错误时立即停止，不要循环重试；告诉用户请求过多，至少等待 30–60 秒后只重试一次。

## 下单

下单必须绑定到一个餐次。一次订单只处理早餐、午餐或晚餐中的一餐：

1. 先确定下单餐次。用户已经指定就直接沿用；没有指定就问“下单哪一餐：早餐、午餐还是晚餐？”
2. 只对选定餐次的商品调用 `calculate-price`，不要把全天餐单一起报价。
3. 展示门店、餐次、餐品、数量、总价和取餐方式。默认外带，用户改说堂食时再切换取餐方式。
4. 询问一次是否确认创建订单。
5. 用户确认后调用 `create-order`，订单只包含选定餐次的商品。
6. 返回订单结果和支付入口；不要自动支付，也不要声称已经支付成功。

用户想买另一餐时，重新确认餐次并单独报价下单，不要把两餐合并成一次订单。用户只说“全都要”时，也要先确认从哪一餐开始。

餐单阶段只报价、不建单。建单是有外部影响的操作，不能在用户没有确认时执行。

## 输出格式

只要输出具体餐单，就必须同时输出菜单和对应营养成分表。默认按以下顺序返回，不先讲背景：

### 1. 今日目标

用 2–3 行说明当前条件、目标量和数据性质：

```text
当前：85kg｜男｜每周 2–3 小时｜到店自取
目标：能量约 1836 kcal｜碳水 187g｜蛋白质 119g｜脂肪 68g
说明：这是谭成义框架的起始估算。
```

### 2. 菜单与营养表

用一张表同时列出餐次、餐品、份量和营养成分。单位为能量 kcal、碳水/蛋白质/脂肪 g、钠 mg；表内数值按该行实际份量计算，不是每 100g。每餐商品后先列“小计”；只有全天方案才在最后增加“全天合计”。

| 餐次 | 餐品 | 份量 | 能量 kcal | 碳水 g | 蛋白质 g | 脂肪 g | 钠 mg | 来源 |
| --- | --- | ---: | ---: | ---: | ---: | ---: | ---: | --- |
| 早餐 | 餐品 A | 1 份 | 320 | 42 | 18 | 9 | 480 | MCP |
| 早餐 | 餐品 B | 1 份 | 160 | 8 | 12 | 8 | 320 | MCP |
| 早餐小计 |  |  | 480 | 50 | 30 | 17 | 800 |  |
| 午餐 | 餐品 C | 1 份 | 620 | 72 | 38 | 20 | 900 | MCP |
| 午餐小计 |  |  | 620 | 72 | 38 | 20 | 900 |  |
| 晚餐 | 餐品 D | 1 份 | 560 | 55 | 34 | 22 | 850 | MCP |
| 晚餐小计 |  |  | 560 | 55 | 34 | 22 | 850 |  |
| 全天合计 |  |  | 1660 | 177 | 102 | 59 | 2550 |  |

表格规则：

- 来源只写 `MCP`、`用户提供` 或 `估算`，不要混写成长句。
- 只有真实拿到的数值才填；缺失项写 `—`，不要补成 0。
- 估算有区间时直接写 `300–350`；不要制造虚假的小数精度。
- 用户已经吃过的餐次也放进同一张表，来源标为 `用户提供` 或 `估算`，并在餐品后标“已吃”。
- 早餐、午餐、晚餐按实际安排增减；不为了凑格式虚构没有的餐次。
- 用户只指定一餐时，只列该餐商品和“本餐合计”，不生成“全天合计”，除非用户同时提供了其他餐次。

### 3. 合计与差额

全天方案在营养表后用 3–4 行说明：

```text
已吃：无
本单：1660 kcal｜碳水 177g｜蛋白质 102g｜脂肪 59g
当日累计：1660 kcal｜碳水 177g｜蛋白质 102g｜脂肪 59g
相对目标：能量 −176 kcal｜碳水 −10g｜蛋白质 −17g｜脂肪 −9g
```

单餐方案写：

```text
本餐：560 kcal｜碳水 55g｜蛋白质 34g｜脂肪 22g
说明：本餐之外的其他餐次未计入，暂不计算全天差额。
```

差额统一按“当日累计 − 目标”计算：负数是还差多少，正数是已经超出多少。只有在用户提供其他餐次或已吃食物时，才计算“当日累计”和“全天差额”。最后提醒估算仍有误差。

### 4. 下一步

默认只给一套方案。下单动作必须带餐次：

```text
下一步：晚餐这套报价并下单吗？
```

用户要求报价或下单时，另加订单摘要，不把价格塞进营养表：

| 门店 | 餐次 | 取餐方式 | 商品 | 数量 | 单价（元） | 小计（元） |
| --- | --- | --- | --- | ---: | ---: | ---: |
| 门店名称 | 晚餐 | 外带 | 餐品 A | 1 | 19.90 | 19.90 |
| 合计 |  |  |  |  |  | 19.90 |

用户只要菜单时，仍保留菜单与营养表，但可以省略目标对比；单纯浏览菜单分类时不必强行给表。用户要比较方案时，每套方案各用一组上述表格，不要把所有方案塞进一张大表。

用户只问“这餐怎么换”时，只展示替换的一餐、该餐营养小计和更新后的全天差额。

## 安全边界

- 不承诺减重结果，不根据单次体重变化建议限制饮食。
- 未满 18 岁、孕期或哺乳期、有饮食障碍经历、慢性病，或正在使用体重相关药物时，不计算个性化减脂目标；仍可提供一般菜单信息，并建议咨询医生或注册营养专业人员。
- 用户提到严重过敏时，提醒核对配料、酱料和门店交叉接触风险；不能只凭菜名保证安全。
- 不把资料中的“男女生理差异”解释成已经确立的生理事实，不把 6–8g 盐建议推广给所有人。
